# DataMapper Canonicalize Guide

This shared guide is loaded by DataMapper interview or migration guides after they have gathered and confirmed the
semantic field mappings.

It first decides which transformation engine to use (Groovy or XSLT), then enriches the semantic mappings accordingly:
XSLT-ready structural information (exact XPaths, target elements, pattern/approach) for XSLT, or a simplified
semantic-only table for Groovy. It then confirms the enriched table with the user and writes the canonical
`### DataMapper:` section to the active pipeline design spec.

**Context provided by the calling guide:**
- Semantic field mappings table (source field, src type, target field, tgt type, transformation, how)
- Conditional mappings table (if any)
- Collection mappings table (if any)
- Source-type and target-type (`JSON_SCHEMA`, `XML_SCHEMA`, or `Primitive`)
- Source and target schema paths (or `"none"`)
- Source parameters table (if any)
- Namespace map (prefix → URI)
- Mapping ID (`kaoto-datamapper-{8hexchars}`, already generated by calling guide)
- Flow name

---

## Step 0: Choose Transformation Engine

Before any structural enrichment, decide which transformation engine to use. This decision determines whether the remaining steps compute XSLT-specific data (XPaths, Target Elements) or skip directly to a simplified Groovy path.

**Count the field mapping rows** in the semantic field mappings table. Exclude collection header rows (e.g., `payload.items[] → items[]` with transformation = `for-each`) — these represent iteration boundaries, not individual field mappings. Count only leaf field mappings.

**Decision rules (evaluated in order):**

| # | Condition | Engine | Reason |
|---|-----------|--------|--------|
| 1 | Both source-schema AND target-schema are `"none"` | **Groovy** | No schemas to drive XSLT structure |
| 2 | Field count < 20 | **Groovy** | Small mapping — inline script is simpler and more readable |
| 3 | Field count ≥ 20 AND at least one schema exists | **XSLT** | Large mapping with schema — XSLT + Kaoto IDE visual editor |

**Log the decision:**

```
Transformation Engine: {Groovy (inline) | XSLT (camel-xslt-saxon)}
Reason: {no schemas for both source and target | field count {N} < 20 | field count {N} ≥ 20 with schemas}
```

**Routing:**
- If Engine = **XSLT** → proceed to [Pre-check](#pre-check-validate-sourcetarget-types) (unchanged XSLT flow through Step 6)
- If Engine = **Groovy** → skip to [Step 1G: Groovy Canonicalization](#step-1g-groovy-canonicalization)

---

# XSLT Path

The following sections (Pre-check through Step 6) apply only when the engine decision is **XSLT**. They are unchanged from the original flow.

---

## Pre-check: Validate Source/Target Types

Before proceeding, verify that source-type and target-type are correct:

**`Primitive` means a truly scalar value** — a single string, number, or boolean. NOT a JSON object, NOT an XML document.

If ANY field mapping references nested paths (e.g., `payload.obj.field`, `payload.array[].item`), the type MUST be `JSON_SCHEMA` or `XML_SCHEMA`, even if no schema file exists. A missing schema file does not make the data Primitive — it just means the schema path is `"none"`.

**Auto-correct rule:** If source-type or target-type is `Primitive` but field mappings contain dotted paths (e.g., `payload.main.temp`) or array access (e.g., `payload.items[]`):
- If the calling guide detected JSON format: change to `JSON_SCHEMA`
- If the calling guide detected XML format: change to `XML_SCHEMA`
- Log: `⚠️ Corrected {source|target} type from Primitive to {JSON_SCHEMA|XML_SCHEMA} — field mappings indicate structured data.`

---

## Step 1: Determine XSLT Pattern and Approach

Select the XSLT generation pattern based on source-type and target-type:

| Source | Target | Pattern | `xsl:output method` |
|--------|--------|---------|---------------------|
| XML_SCHEMA | XML_SCHEMA | A — XML→XML | `xml` |
| JSON_SCHEMA | JSON_SCHEMA | B — JSON→JSON | `text` |
| JSON_SCHEMA | XML_SCHEMA | C — JSON→XML | `xml` |
| XML_SCHEMA | JSON_SCHEMA | D — XML→JSON | `text` |
| Primitive | XML_SCHEMA | A (no namespace prefix on source) | `xml` |
| Primitive | JSON_SCHEMA | B (source is simple value) | `text` |
| Any | Primitive | value-of only | `text` |

**Determine Approach (JSON source only):**

| Condition | Approach |
|-----------|----------|
| Source is `JSON_SCHEMA` AND no source parameters | **A** — `useJsonBody: true` |
| Source is `JSON_SCHEMA` AND source parameters exist | **B** — manual header param |
| Source is `XML_SCHEMA` or `Primitive` | **N/A** — no JSON handling |

---

## Step 2: Compute Source XPath for Each Field

For each row in the semantic field mappings table, derive the exact XPath expression that `camel-implement` will use in the XSLT `select="..."` attribute.

### JSON_SCHEMA source — Approach A (useJsonBody: true)

When `useJsonBody: true`, Camel converts the JSON body to lossless XML before Saxon starts. The XSLT receives lossless XML as its input document. Navigate using absolute XPath from the root.

**Translation rules — strip `payload.` prefix, translate each segment:**

| Semantic path | Field type | Source XPath |
|---|---|---|
| `payload.field` | string | `/fn:map/fn:string[@key='field']` |
| `payload.field` | number | `/fn:map/fn:number[@key='field']` |
| `payload.field` | boolean | `/fn:map/fn:boolean[@key='field']` |
| `payload.obj.field` | string | `/fn:map/fn:map[@key='obj']/fn:string[@key='field']` |
| `payload.obj.nested.field` | number | `/fn:map/fn:map[@key='obj']/fn:map[@key='nested']/fn:number[@key='field']` |
| `payload.arr[]` (for-each) | array | `/fn:map/fn:array[@key='arr']/fn:map` |
| `payload.arr[].field` (inside for-each) | string | `fn:string[@key='field']` *(relative — no leading `/fn:map/`)* |
| `payload.arr[0].field` (single item) | string | `/fn:map/fn:array[@key='arr']/fn:map[1]/fn:string[@key='field']` *(XPath is 1-based)* |

**Key rules:**
- Intermediate segments (objects on the path to a leaf field) always use `fn:map[@key='...']`
- Only the **last** segment uses the typed element (`fn:string`, `fn:number`, `fn:boolean`)
- Array iteration paths use `fn:array[@key='...']/fn:map` as the `xsl:for-each` select — then fields inside use **relative** paths (no root prefix)
- Single indexed access: DataWeave `[0]` → XPath `[1]` (XPath is 1-based)

### JSON_SCHEMA source — Approach B (manual header param)

Same rules as Approach A, but replace the leading `/` with `$body-x/`:

| Semantic path | Field type | Source XPath |
|---|---|---|
| `payload.field` | string | `$body-x/fn:map/fn:string[@key='field']` |
| `payload.obj.field` | number | `$body-x/fn:map/fn:map[@key='obj']/fn:number[@key='field']` |
| `payload.arr[]` (for-each) | array | `$body-x/fn:map/fn:array[@key='arr']/fn:map` |
| `payload.arr[].field` (inside for-each) | string | `fn:string[@key='field']` *(relative — same as Approach A)* |

Where `body` is the `xsl:param` name. If the source parameter has a different name (e.g., `orderPayload`), use `$orderPayload-x/fn:map/...` instead.

### XML_SCHEMA source

Use namespace prefix from the namespace map:

| Semantic path | Source XPath |
|---|---|
| `payload.field` | `/ns0:Root/ns0:field` |
| `payload.obj.field` | `/ns0:Root/ns0:obj/ns0:field` |
| `payload.items[]` (for-each) | `/ns0:Root/ns0:items` |
| `payload.items[].field` (inside for-each) | `ns0:field` *(relative)* |

Where `Root` is the root element name from the XSD, and `ns0` is the source namespace prefix from the namespace map.

**If the XML has no namespace** (no `ns0` in namespace map), omit the prefix: `/Root/field`.

### Primitive source

| Condition | Source XPath |
|-----------|-------------|
| Field path exists in table | Use field path as best-effort XPath segment (e.g., `fieldName`) |
| No field path (truly primitive) | `.` (context node) |

---

## Step 3: Compute Target Element for Each Field

For each row, derive the exact XSLT element that `camel-implement` will generate in the output.

### JSON_SCHEMA target

Map the target field type to its lossless XML element:

| Target type | Target Element |
|---|---|
| string | `<string key="{targetField}">` |
| number | `<number key="{targetField}">` |
| boolean | `<boolean key="{targetField}">` |
| object | `<map key="{targetField}">` |
| array | `<array key="{targetField}">` |

For nested targets (e.g., `result.status`): the intermediate objects are `<map key="...">` wrappers, and only the leaf uses the typed element.

### XML_SCHEMA target

| Condition | Target Element |
|-----------|---------------|
| Target has namespace | `<{targetField} xmlns="{target-namespace}">` or `<ns1:{targetField}>` |
| Target has no namespace or is inside namespaced root | `<{targetField} xmlns="">` (to reset namespace) |
| Target is an attribute | `<xsl:attribute name="{targetField}">` |

### Primitive target

`xsl:value-of` only — no wrapping element needed. Target Element column = `(value-of)`.

## Step 5: Write Enriched Design Spec Section

**CRITICAL — do not save an empty Field Mappings table.** If the Field Mappings table has no data rows, do NOT append the DataMapper section. Instead, report:

```
❌ ERROR: DataMapper has no field mappings defined.

The XSLT cannot be generated from an empty mapping table — an empty skeleton
would be functionally useless and cannot be fixed by Kaoto IDE alone.

Action required:
1. If this is a migration: run the DataWeave conversion analysis to extract field mappings.
2. If this is a greenfield flow: return to `camel-brainstorm` and complete the data transformation interview.
3. Then re-run the current command.
```

**Stop here — do not write the design spec section.**

# Groovy Path

The following sections apply only when the engine decision in Step 0 is **Groovy**. They replace the XSLT-specific Steps 1–6 above.

---

## Step 1G: Groovy Canonicalization

Determine the format pair from source-type and target-type. This is the same lookup as XSLT Step 1 but without XSLT-specific labels:

| Source | Target | Format Pair |
|--------|--------|-------------|
| XML_SCHEMA | XML_SCHEMA | XML → XML |
| JSON_SCHEMA | JSON_SCHEMA | JSON → JSON |
| JSON_SCHEMA | XML_SCHEMA | JSON → XML |
| XML_SCHEMA | JSON_SCHEMA | XML → JSON |
| Primitive | XML_SCHEMA | Primitive → XML |
| Primitive | JSON_SCHEMA | Primitive → JSON |
| Any | Primitive | Any → Primitive |

**Do NOT compute Source XPaths or Target Elements.** Groovy uses dot notation for navigation and Groovy map/builder syntax for output — the semantic field paths from the calling guide are sufficient.
