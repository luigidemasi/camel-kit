# Task Template — Greenfield Projects

> **Context:** Loaded by `camel-plan` for greenfield (new integration) projects.
> **Purpose:** Template for generating per-flow implementation tasks.

---

## Structured Metadata

Before the Markdown task sections, emit one `yaml plan-metadata` block that mirrors the task list. Populate:
- `files.creates` / `files.modifies` / `files.reads` from each task's **Files** section
- `provides.routes` for generated route IDs
- `provides.endpoints` for `direct:`, `seda:`, `timer:`, `kafka:`, HTTP, and other endpoints introduced by a task
- `provides.properties` for property keys generated by properties tasks
- `provides.schemas`, `provides.testData`, `provides.beans`, `provides.externalServices`, and `provides.routeContracts`
  when those artifacts are produced
- matching `consumes.*` entries for resources a task needs from another task
- `dependsOn` for ordering that should be explicit even without an overlapping resource

Example:

```yaml plan-metadata
tasks:
  - id: 2
    title: Generate Route YAML - order-ingestion
    files:
      creates:
        - src/main/resources/camel/order-ingestion.camel.yaml
    provides:
      routes:
        - order-ingestion
      endpoints:
        - direct:validate-order
    consumes:
      properties:
        - orders.input.dir
    dependsOn:
      - 1
```

## Standard Task Sequence per Flow

For each flow in the design spec, generate these tasks in order:

### Task Template: Scaffold Project (once, first flow only)

```markdown
### Task 1: Scaffold Project Structure

**Agent:** implementation-engineer

**Files:**
- Create: runtime-specific directory structure from design spec Section 6
- Create: `[MODULE_DIR]pom.xml` (Spring Boot/Quarkus only)
- Verify/Refresh: project-root `mvnw`, `mvnw.cmd`, `.mvn/wrapper/maven-wrapper.properties`
  (Spring Boot/Quarkus only; installed by `camel-kit init`)

**Guides to Load:**
- `camel-implement/guides/orchestrator.md` — file path table
- `camel-implement/guides/maven-dependencies.md` (Spring Boot/Quarkus only)
- `camel-implement/guides/pom-spring-boot.md` (if Spring Boot runtime)
- `camel-implement/guides/pom-quarkus.md` (if Quarkus runtime)

**POM Template Files (MUST READ AND COPY):**
- If Quarkus: `templates/pom-quarkus.xml` — copy verbatim, replace only `[PLACEHOLDER]` values
- If Spring Boot: `templates/pom-spring-boot.xml` — copy verbatim, replace only `[PLACEHOLDER]` values

<HARD-RULE>
For Main, create the runtime tree from Section 6, do NOT load Maven/POM guides, and do NOT create a POM. For Spring
Boot/Quarkus, do NOT generate the POM from scratch. COPY the runtime's template file and replace ONLY the bracketed
placeholders. The template already has the correct groupIds, artifactIds, repositories, and plugins.
</HARD-RULE>

**Design Spec Section:** Section 6 (Project Structure)

- [ ] Create directory structure from design spec Section 6
- [ ] For Main, verify the module-root route/properties directories exist and `pom.xml` was not created
- [ ] For Spring Boot/Quarkus, create `pom.xml` using the TEMPLATE-COPY approach:
  - If Quarkus: Read the file `templates/pom-quarkus.xml`, copy it verbatim to `[MODULE_DIR]pom.xml`
  - If Spring Boot: Read the file `templates/pom-spring-boot.xml`, copy it verbatim to `[MODULE_DIR]pom.xml`
  - Replace ONLY these placeholders: `[PROJECT_GROUP_ID]`, `[PROJECT_ARTIFACT_ID]`, `[PROJECT_VERSION]`, `[PROJECT_NAME]`, `[PLATFORM_BOM_VERSION]` (and `[SPRING_BOOT_VERSION]` for Spring Boot)
  - Get `[PLATFORM_BOM_VERSION]` from the design spec header `platformBomVersion` field
  - Do NOT modify any other values in the template (groupIds, artifactIds, repositories, plugins)
  - Add project-specific dependencies in the DEPENDENCIES section
- [ ] For Spring Boot/Quarkus, verify the project-root wrapper assets written by `camel-kit init`; if any are missing,
  restore the exact init-managed `mvnw`, `mvnw.cmd`, and `.mvn/wrapper/maven-wrapper.properties` assets and make
  `mvnw` executable
- [ ] For Spring Boot/Quarkus, verify `./mvnw -f [MODULE_DIR]pom.xml help:effective-pom -q` exits 0
- [ ] Verify: `ls -la` shows expected structure

**Review:**
- [ ] Spec compliance: directory structure matches spec Section 6
- [ ] Code quality: Main has no POM; Spring Boot/Quarkus use the correct template groupIds and versions
```

### Task Template: Generate Missing Schemas (per flow, conditional)

Include this task before the route task only when the approved design records missing JSON schemas and explicitly
requires generating them. The route task consumes these schema resources; do not regenerate schemas inside that task.

```markdown
### Task N: Generate Schemas — [flow-name]

**Agent:** implementation-engineer

**Files:**
- Create: `[SCHEMA_DIR][flow-name]-input.json`
- Create: `[SCHEMA_DIR][flow-name]-output.json`

**Guides to Load:**
- `camel-implement/guides/orchestrator.md` — resolve runtime `SCHEMA_DIR`
- `camel-implement/guides/schema-generation.md`

**Design Spec Section:** Section 3, Flow: [flow-name], input/output data contracts

- [ ] Confirm the approved design requires generation of the missing schemas
- [ ] Generate input and output schemas from the approved data contracts
- [ ] Record both schema identifiers in this task's `provides.schemas`; make the route task consume them
- [ ] Verify: `test -s [SCHEMA_DIR][flow-name]-input.json && test -s [SCHEMA_DIR][flow-name]-output.json` exits 0

**Review:**
- [ ] Spec compliance: fields, types, and required values match the approved contracts
- [ ] Code quality: valid JSON Schema and runtime-correct paths
```

### Task Template: Generate Route YAML (per flow)

```markdown
### Task N: Generate Route YAML — [flow-name]

**Agent:** implementation-engineer

**Files:**
- Create: `[ROUTE_DIR][flow-name].camel.yaml`
- Create: `[ROUTE_DIR]kaoto-datamapper-*.xsl` (XSLT DataMapper only)

**Guides to Load:**
- `camel-implement/guides/orchestrator.md` — file paths, execution order
- `camel-implement/guides/component-loading.md` — component documentation
- `camel-implement/guides/yaml-catalog-rules.md` — catalog verification rules
- `camel-implement/guides/yaml-structure.md` — YAML DSL structure
- `camel-implement/guides/route-validation.md` — validation loop
- `camel-implement/guides/datamapper-groovy.md` (if Transformation Engine is Groovy)
- `camel-implement/guides/datamapper-approach-[a|b].md` (if Transformation Engine is XSLT)
- `camel-implement/guides/datamapper-validation.md` (if DataMapper)
- `shared/datamapper-canonicalize.md` (if DataMapper)
- `camel-implement/guides/sequential-http-calls.md` (if HTTP→HTTP)

**MCP Tools:**
- `camel_catalog_component_doc(component="[source-component]", runtime="[runtime]", platformBom="[bom]")`
- `camel_catalog_component_doc(component="[sink-component]", runtime="[runtime]", platformBom="[bom]")`
- `camel_catalog_eip_doc(eip="[eip]", runtime="[runtime]", platformBom="[bom]")` for each EIP used
- `camel_catalog_dataformat_doc(dataformat="[format]", runtime="[runtime]", platformBom="[bom]")` for each data format
- `camel_catalog_language_doc(language="[language]", runtime="[runtime]", platformBom="[bom]")` for each language used

**Design Spec Section:** Section 3, Flow: [flow-name]

- [ ] Read design spec Section 3 for flow [flow-name]
- [ ] Load and follow orchestrator.md Steps 1-2 (DataMapper then Route Generation)
- [ ] Verify each component via MCP catalog before writing YAML
- [ ] Generate `[flow-name].camel.yaml` with:
  - Route ID: `[flow-name]`
  - Description: [from spec]
  - Source: `[component]` with options from MCP catalog
  - Transformations: [from spec, each EIP MCP-verified]
  - Sink: `[component]` with options from MCP catalog
  - Error handling: [strategy from spec]
- [ ] Self-validate: route has routeId, description, source, sink, no hardcoded values
- [ ] Verify: `test -f [ROUTE_DIR][flow-name].camel.yaml && echo "EXISTS"`

**Review:**
- [ ] Spec compliance: components match spec, structure matches spec, all transformations present
- [ ] Code quality: constitution rules 1-7, no anti-patterns, Kaoto-compatible YAML
```

### Task Template: Generate Properties (per flow or consolidated)

```markdown
### Task N: Generate Application Properties — [flow-name]

**Agent:** implementation-engineer

**Files:**
- Create/Modify: `[PROPS_DIR]application.properties`

**Guides to Load:**
- `camel-implement/guides/properties-generation.md`

**Design Spec Section:** Section 3, Flow: [flow-name], Configuration Properties

- [ ] Read design spec configuration properties for [flow-name]
- [ ] Write concrete `key=value` entries to runtime `PROPS_DIR`; route YAML references those keys as `{{key}}` in every
  runtime
- [ ] Only when one property value interpolates another property, use `{{other.key}}` for Main or `${other.key}` for
  Spring Boot/Quarkus
- [ ] For Main: include `camel.jbang.dependencies`; do not create a POM
- [ ] Verify: `grep "[flow-name]" [PROPS_DIR]application.properties`

**Review:**
- [ ] Spec compliance: all properties from spec present
- [ ] Code quality: no hardcoded values, proper grouping
```

### Task Template: Generate Main Run Script (consolidated)

Include this task once per module after all route and properties tasks, and only for Main. Spring Boot/Quarkus use
their Maven launch commands and must not receive `run.sh`.

```markdown
### Task N: Generate Main Run Script

**Agent:** implementation-engineer

**Files:**
- Create: `[MODULE_DIR]run.sh`

**Guides to Load:**
- `camel-implement/guides/run-script.md`

**Design Spec Section:** Section 3 (all module flows), Section 6 (Project Structure)

- [ ] Inventory every module `.camel.yaml` route as `ROUTE_FILES`
- [ ] Inventory every module XSLT DataMapper file as `XSL_FILES` (the list may be empty)
- [ ] Generate one `run.sh` whose single Camel command lists every `ROUTE_FILES` and `XSL_FILES` entry
- [ ] Make the script executable with `chmod +x [MODULE_DIR]run.sh`
- [ ] Verify: `test -x [MODULE_DIR]run.sh` exits 0 and the command contains every inventoried route/XSL file

**Review:**
- [ ] Spec compliance: the script launches the complete module, not one flow
- [ ] Code quality: JBang alias, properties argument, and strict shell flags match the run-script guide
```

### Task Template: Generate Docker Compose (consolidated)

Include this task only when at least one flow declares an external service dependency. Omit it entirely when none do,
for all runtimes (including Main).

```markdown
### Task N: Generate Docker Compose

**Agent:** implementation-engineer

**Files:**
- Create: `[MODULE_DIR]docker-compose.yaml`

**Guides to Load:**
- `camel-implement/guides/docker-compose.md`

**Design Spec Section:** Section 3 (all flows, external service dependencies)

- [ ] Identify all external services from all flows (databases, brokers, APIs)
- [ ] For Main, inventory and pass every module `.camel.yaml` route and every XSLT DataMapper file to the guide; do not
  reduce the application command to the current flow
- [ ] Generate docker-compose.yaml with service definitions
- [ ] Verify: `docker compose -f [MODULE_DIR]docker-compose.yaml config`

**Review:**
- [ ] Spec compliance: all external services from spec have docker-compose entries
- [ ] Code quality: proper networking, health checks, volume mounts
```

After all implementation and Citrus test-generation tasks, do not add separate
validation or smoke-test tasks. `camel-execute` performs the cross-cutting review
and runs the internal build-or-smoke plus Citrus verification loop once; chained
runs then continue to report-only `/camel-validate` as Phase 4.
